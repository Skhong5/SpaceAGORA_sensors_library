- **No method overwriting.** `ext/SpaceAGORAPlotlyJSExt.jl` defines its own
  `PlotlyJSRenderer` and adds methods to core's private figure functions for
  that type only (for example `Reports._metric_summary_figure(::PlotlyJSRenderer,
  batch)`). It overwrites no core method, so precompilation accepts it.
- **The refusal.** Without the extension, the figure functions throw
  `PlotlyJSUnavailableError`. Its message names both remedies: add PlotlyJS to
  the environment and load it, or set the two plot flags to false. A planner
  comparison refuses before any planner runs (`planner_comparison.jl`), as Giusy
  decided on 2026-10-21.
- **Project.** PlotlyJS moves from `[deps]` to `[weakdeps]` with the
  `SpaceAGORAPlotlyJSExt` extension.
- **Unchanged outputs.** 144 of 145 report fingerprints are identical to C4-5. The
  one difference is the removed qualified binding `GuidanceHooks.PlotlyJS`, which
  the migration notes record.
- **Found by hosted CI and fixed.** In `optional-hypr-installation`, the core-first
  integration campaign (`test/optional/hypr/optional.jl`) includes
  `test/unit/rpo_port_tests.jl`, which loads PlotlyJS to make the comparison
  figures. The HYPR integration environment had PlotlyJS only through
  SpaceAGORA's dependencies, so with PlotlyJS a weak dependency the load failed
  ("Package PlotlyJS not found"). `52cf6a5fa` adds PlotlyJS to that environment
  in `test/optional/hypr/setup.jl`, as a user's plotting project would
  (`Pkg.add` with every existing version preserved). The builder checked every
  job that runs test or example files from a companion's environment (HYPR,

## Residual Risk

- **A breaking change for plotting scripts.** Scripts and projects that plot must add and load PlotlyJS. SpaceAGORA 0.5.1 announced it, and the Upgrading page and the error message give the steps.
- **Configurations with only `write_plotly_outputs=false`** now refuse without PlotlyJS. They need `write_failed_path_outputs=false` too.
- **The PlotlyJS stack floats** in the examples and test environments, as the rest of the plotting stack does by decision; only Roots is pinned.
- **The renderer registry is process-global.** Sandboxed source loads (suites 01 and 03) keep their own registry, and only the package's extension registers. A sandbox copy therefore has no renderer unless PlotlyJS's extension is loaded for it, and its figure functions refuse.
- **The full sysimage** no longer bakes in PlotlyJS, so plotting sessions with that image compile PlotlyJS and the extension at first use.
