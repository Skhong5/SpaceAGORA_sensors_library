# PR review: pre-run warning for unpaired Apollo descent guidance and control

## Scope

Review of PR 337 (branch `apollo-pairing-check`, head `6eed7b858`) against `main` at `58b8dbc40`: `git diff main...apollo-pairing-check`. One commit. `ApolloDescentControlModel` gains a `SimulationLifecycle.preflight_control` method. When a configuration has both Apollo guidance and Apollo control, the method logs one warning (`maxlog=1`) if any spacecraft is controlled or guided without its counterpart on the same `ApolloDescentState`. The docstring and the lunar landing page describe the check.

## Findings

Author's notes for the reviewer (no P1 or P2 known to the author):

- Confirmed defect (V13): on `main`, `calcControlEffect!` returns with zero thrust while `state.phase_start_s[1, i]` is `NaN` (the "nothing to track until the guidance has issued its first command" branch), and only `ApolloDescentGuidanceModel` sets it. With the guidance on another state object, the control never thrusts and nothing reports it. The new closed-loop test reproduces this: after the run, the control's `phase_start_s` is all `NaN` and its thrust is zero.
- Low, scope choice: configurations with only Apollo guidance or only Apollo control are not checked, because a user's guidance could write the state, or guidance could run alone. The PI decided this scope on 2026-10-15.
- Low, `maxlog=1`: the warning is shown once per Julia session (the design's mechanics for checks that will become errors). A second mismatched configuration in the same session does not warn again.
- Note: `run_simulation` calls `preflight_control` for each control effector, before `isolate_state` copies the configuration (`execution.jl:546-551`), and again if the parallel flag re-enters `run_simulation`. The check is repeated in those cases; `maxlog=1` keeps it to one message.
- Note: configuration and terrain agreement, which the guidance docstring also asks for, are not checked.
- Note: `import ..GuidanceHooks` is already present in `ControlHooks` (from `control/energy_depletion_lifecycle.jl`); repeating it in this file keeps the file independent of include order.

Reviewer to verify:

- The grouping by `IdDict` on the state matches the run's actual pairing: guidance writes and control reads only `model.state` for indices in `spacecraft_indices` (both models, including copies made by `bind_spacecraft`, which keep `m.state`).
- No configuration in `examples/`, `scripts/`, `test/` or `docs/` that pairs Apollo models now warns (the author found the closed-loop tests, `scripts/dev/viewer_demos/apollo11_landing.jl` and the docs example all build both models from one state with the default or the same selection).
- The new tests fail on `main` (no `preflight_control` method for the type, so no warning is logged).
- The hook is not in `src/orchestration/simulation/engine/setup.jl`, which another branch changes.

## P1 Assessment

No P1 findings known to the author. The method only reads `args.guidance_model.guidance_effectors` and `args.control_model.control_effectors` and logs; it mutates nothing and throws nothing. Paired configurations run bitwise identically (see the evidence below).
