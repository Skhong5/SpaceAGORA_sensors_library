# Review record: PR 509: Keep the burn scheduler's commands and plans, and the orbit counter, in checkpoint files

## Scope

Review of the SpaceAGORA `resume-maneuver-buffers` branch against main 0f03bbfce: a
fix for main, found while building C-3d (#507) and confirmed there by the in-house
review's lead on its P3-7 (2026-10-23). A run with the burn scheduler
(`BaseThrusterModel`) and a maneuver guidance model, checkpointed and resumed, lost
a maneuver command or burn plan that was waiting at the checkpoint; and every
resumed run counted its spacecraft's orbits from the first again.

What it does:
- **The entry.** The checkpoint's run state holds `maneuver_buffers` (version 1):
  `SharedBuffers.maneuver_commands` and `SharedBuffers.maneuver_burn_plans`, the
  command each spacecraft's maneuver guidance last issued and the plan installed
  for it. It is written only when some entry differs from its default.
- **The restore.** A resumed run copies both back in `_resume_engine_state!`,
  before its models start and its callbacks initialize, so the scheduler's first
  pass finds what the unbroken run's next segment finds. A checkpoint without the
  entry resumes with the defaults; one for another number of spacecraft is
  refused.
- **The orbit counter.** The run state also holds `orbits` (version 1),
  `p.orbit_counter`, written once some spacecraft is past its first orbit and
  restored with the buffers, so a resumed run continues the count.
- **The docs.** The outputs page says what the checkpoint now holds and what an
  earlier checkpoint does on a resume; the architecture page's run-state table
  gains both entries, the opt-in GRAM caches and the state a checkpoint does not
  need (F6).

Rule: every run that is not resumed is bitwise unchanged, and so is every
checkpoint file written while both buffers hold their defaults and every
spacecraft is on its first orbit.

## Findings

- **F1 (the cause).** On main 0f03bbfce, a three-spacecraft run with
  `ApoapsisTargetPeriapsisRaiseGuidanceModel` and one burn scheduler, checkpointed
  every 7000 s of 14000 and resumed at 7000 s, did not end where the run without
  the break ends; with the scheduler alone it did. Recording both buffers at each
  solve start showed why: the unbroken run starts its second segment with a valid
  command and plan for every spacecraft, and plans and flies its burns after it,
  while the resumed run starts with none and never burns.
- **F2 (the orbit counter).** #507's campaign case still resumed wrongly with F1
  fixed: the unbroken run starts its second segment on orbit 2 and plans orbit 2's
  maneuver, while the resumed run starts on orbit 1 and plans orbit 1's again,
  since `p.orbit_counter` was not in the checkpoint. The orbit-count mission end
  reads the same counter: on main, a `MissionOrbits` run of two orbits,
  checkpointed every 4000 s and resumed after the first checkpoint, ended an
  orbit late. With the counter restored it ends at the same time, bit for bit.
- **F3 (written only when set).** Each entry is left out while it holds its
  default: every command and plan unset, every spacecraft on its first orbit.
  Such a checkpoint is the file earlier versions wrote, and resuming it gives the
  defaults the entry would have restored. So the checkpoints of other runs, and of
  runs shorter than an orbit, do not change.
- **F4 (where the restore goes).** The buffers and the counters belong to the
  engine's run state, like the activity flags and the callbacks' state, and are
  restored with them before the models' initializers. No initializer writes them:
  the buffers are written only by the maneuver guidance models and the
  scheduler's passes, and the counters by the apoapsis callback and the state
  anchors.
- **F5 (what reads the counter).** On main, `p.orbit_counter` is read by:
  - the apoapsis callback
    (`src/orchestration/simulation/callbacks/event_callbacks.jl`), which counts
    the orbits and ends a `MissionOrbits` run once every active spacecraft has
    completed `number_of_orbits`. **Tested:** the `MissionOrbits` resume test;
  - `AerobrakingCampaignPropulsiveManeuverGuidanceModel`
    (`src/models/gnc/guidance/maneuvers/thruster_guidance_functions.jl`), which
    issues the maneuver whose `maneuver_orbit_number` is the current orbit.
    **Tested:** the campaign round trip, past its first orbit at the halfway
    checkpoint;
  - `ApoapsisTargetPeriapsisRaiseGuidanceModel` (same file), which labels its
    command with the orbit (`source_orbit`); the label goes into the plan and
    into the burn scheduler's rejection records. A label only; not tested on its
    own;
  - the pass-indexed density model `PassKeyedExponentialAtmosphereModel`,
    through `pass_exponential_density` in
    `src/orchestration/simulation/callbacks/density_callbacks/runtime.jl`, which
    takes the density of flight pass `orbit_counter + counter_pass_offset`. Not
    tested;
  - the periapsis pulses
    (`src/orchestration/simulation/callbacks/state_anchor_callbacks.jl`), which
    pulse each listed pass `orbit_counter + counter_pass_offset` once. Not
    tested;
  - the burn scheduler's maneuver event log
    (`src/models/gnc/control/maneuvers/propulsive_maneuvers.jl`) and the density
    pass log, which write the orbit in a column. Diagnostics; not tested.

  The state anchors (same file as the pulses) write the counter when an anchor
  carries an `orbit_count`; a count an anchor set before the checkpoint now
  survives the resume as well. `_requires_guidance_orbit_counter` (density
  callbacks' assembly) decides only whether the apoapsis callback is installed,
  and external propagation refuses orbit-count termination; neither reads the
  value. Every reader reads the same vector, and the unit check of the entry
  compares it restored, so the untested readers see the unbroken run's count too.
- **F6 (the sweep: other run state outside the checkpoint).** Every field of
  `ODEParams` and `SharedBuffers`, and the state the callbacks keep in their
  closures, was checked for state that changes during a run and carries from one
  checkpoint segment to the next. Model-owned state goes through
  `checkpoint_state` (the `models` entry) and is not repeated here.

  | Run state | In the checkpoint | If it were not |
  | --- | --- | --- |
  | `is_active` | yes, `activity` | — |
  | interlink selection and flags | yes, `interlinks` | — |
  | batteries, faults, sensors, hinge, gimbal and firing state | yes, `callbacks` | — |
  | periodic tick clocks | yes, `periodic_ticks` | — |
  | GNC and effector scopes | yes, `gnc_scopes` and `effector_scopes` (checked, not restored) | — |
  | saved results rows | yes, `results_rows` | — |
  | `maneuver_commands`, `maneuver_burn_plans` | now, `maneuver_buffers` | a waiting maneuver was lost (F1) |
  | `orbit_counter` | now, `orbits` | the count restarted at orbit 1 (F2, F5) |
  | `in_atmosphere`, `in_atmosphere_sample_t` | no | none: recomputed from the state at each solve's start |
  | densities, temperatures, winds, `density_sample_t`, `heat_rates`, the save cache | no | none: sampled again from the state; restoring them in a probe changed nothing, and a drag run resumed by the kit's round trip matches bit for bit |
  | state anchors' next anchor, periapsis pulses' last pass, sensor and other callbacks' own counters | no, or through `callbacks` | none: reset or rebuilt at each solve's start, as at a segment's start in the unbroken run |
  | GRAM track and vacuum-prediction caches | no | opt-in (`SPACEAGORA_GRAM_TRACK_CACHE`, `SPACEAGORA_VACUUM_GRAM_CACHE`, both off by default): a resumed run builds them again, so its interpolated densities can differ within the caches' tolerances. Not tested |
  | GRAM density perturbation walk | no | a resume is refused |
  | plume-surface erosion integral | no | documented: a resumed run starts a new diagnostic integral; the forces do not read it |
  | `et_start`, `current_time`, `solve_segment_end_time` | no | none: set from the configuration or by each solve |
  | ephemeris and SPICE memos, workspaces, execution plans and tuners, cost telemetry | no | none: they change only how fast a run goes |

  So the two entries here are the last engine-owned run state of their kind.
  The architecture page's table now lists the new entries, the caches and the
  state that comes back by itself.
- **F7 (older checkpoints, and why there is no warning).** A checkpoint without
  `maneuver_buffers` or `orbits` resumes as before, with no error and no
  warning: each restore returns at once when its entry is missing. The test
  strips both entries from a real checkpoint of the two-orbit run, past its first
  orbit, and resumes it: no error, and the run ends late, as it did before. A
  warning for a resumed run past
  its first orbit whose checkpoint has no `orbits` entry is not added, because
  the run cannot tell that case apart. An entry is left out on purpose while
  every spacecraft is on its first orbit (F3), and the checkpoint does not record
  which SpaceAGORA wrote it (its schema version is unchanged). An orbit count
  estimated from the resume time and the orbital elements need not match the
  apoapsis callback's count either: a state anchor can set the count, and a run
  need not start at apoapsis. The outputs page says instead what a resume from
  such a checkpoint does (a `MissionOrbits` run ends late, the campaign guidance
  repeats the maneuvers already flown) and how to run it again.
- No P1 or P2 finding.

## P1 Assessment

No P1 finding.
- A run that is not resumed reads the buffers and the counters once per
  checkpoint and never writes them back, so its bits do not change; a resumed
  run's buffers and counters are the unbroken run's at the checkpoint (Tests

## Residual Risk

- **Older checkpoints.** A checkpoint written before this fix holds neither
  entry, so a run resumed from one still starts with no command or plan waiting
  and on the first orbit, as before (F7). The outputs page says what that does to
  a run past its first orbit.
- **Untested counter readers.** The pass-indexed density model, the periapsis
  pulses and the logs read the restored counter but have no resume test of their
  own (F5).
- **Opt-in GRAM caches.** With `SPACEAGORA_GRAM_TRACK_CACHE` or
  `SPACEAGORA_VACUUM_GRAM_CACHE` on, a resumed run's densities can differ from
  those of a run never interrupted, within the caches' tolerances (F6). Not
  changed here.
- **Run state of user models.** A user model that keeps run state of its own
  outside `checkpoint_state` is not covered, as before.
- **Not run locally:** `builtin_conformance_tests` with the EDG companion, the EDG
  tests under `test/gnc/aerobraking`, the examples smoke and the whole unit tree
  in its own runner, and the coverage shards, which build native GRAM. Hosted CI
  runs all of them.
