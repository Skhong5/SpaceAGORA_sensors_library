# Review record: PR 476: a resumed run refuses GNC models that act on other spacecraft

## Scope

Review of the SpaceAGORA `gnc-scope-checkpoint` branch against main (`2088b4408`,
after #465, #468, #469 and #470). It fixes a checkpoint admission gap that a
design review of the C-3 GNC scope table found on 2026-10-21 (its third finding).

On main:

- `_model_checkpoint_configuration` names the guidance, navigation and control
  models by type name and position. `_check_model_checkpoint_state` compares that
  list, and `_restore_model_checkpoint_state!` restores each model's
  `checkpoint_state`.
- A model's spacecraft binding is not part of any of it:
  - The momentum manager saves its wheel momentum, held command and tick count,
    not its `spacecraft_index`. Its output follows the current index.
  - The robot-arm controller saves its held torque and warm start, not its
    binding.
- So a run checkpointed with the manager of spacecraft 1 resumed with a manager
  of spacecraft 2 is accepted, and the manager of spacecraft 2 continues from the
  first manager's state. Reproduced on main: the checkpoint at 3 s holds 2 ticks
  and the resumed manager of spacecraft 2 ends at 5, counting on from them.
- When no model keeps run state, no `models` entry exists and nothing about the
  models is compared.

Change:

- A `gnc_scopes` runtime entry, version 1, holds each group's scopes in
  configuration order: `(scope=:all,)`, `(scope=:bound, positions)` or
  `(scope=:coupled, primary, partners)`.
  - A `BoundSpacecraft` and a `SpacecraftSelection` both resolve to sorted run
    positions without repeats, through C-2's `resolve_spacecraft_scope`.
  - The record is taken in `_start_run_models!`, after the run-start initializers
    (RPO resolves its positions there), for every checkpointed or resumed run.
    Every checkpoint of the run writes it.
- `_resume_engine_state!` reads the entry with the other entries and checks its
  version and form before anything is restored.
- `_start_run_models!` compares the run's record with the entry
  (`_check_gnc_scope_baseline`). This happens after the initializers and before
  `_restore_model_checkpoint_state!`, so before any model's run state comes back.
- Legacy rule: a checkpoint without the entry resumes as on main, with a warning
  when the run has a bound or coupled model.
- Docs: the run-state section of the architecture guide, the checkpointing section
  of the outputs page, the RPO pilot's checkpoint table and the extension guide's
  checkpoint section.

not replace an independent review.

Independent review: the coordinator reviewed PR 476 at `fa825a0ee` under Giusy's
delegation on 2026-10-21. It was a read-only review of the diff, without rerunning
the tests.

- **Order of the checks.** `_resume_engine_state!` reads the entry and checks its
  version and groups (`_gnc_scope_checkpoint_entry`) with the other phase-1
  checks, before the activity, interlink and callback restores. In
  `_start_run_models!` the record is taken after every navigation, guidance and
  control initializer, and `_check_gnc_scope_baseline` runs before
  `_restore_model_checkpoint_state!`. So no model's saved state reaches a model
  whose scope differs.
- **Who pays.** The record is built only when the run writes or resumes a
  checkpoint (`checkpoint_active || resumed`), once per run start. The segment
  loop's single `_write_checkpoint!` call passes it, and the keyword defaults to
  `nothing`, so runs without checkpoints compute and write nothing new.
- **Plain data.** Bound positions come from `resolve_spacecraft_scope`, and
  coupled partners are collected into a fresh vector. The record holds no
  reference to a live selection or model.
- **Messages.** A refusal is an `ArgumentError` that names the group, the model's
  position and type, and both scopes in run positions, or both model counts.
- **The legacy rule is a choice.** A checkpoint without the entry resumes as on
  main, warning only when some model is bound or coupled. Refusing instead is
  the one-line alternative the Findings describe; the recommended rule is the one
  built.
- No trailer on the commit. The new test file is registered in
  `test/unit/runtests.jl` after `builtin_checkpoint_state_tests.jl`, away from
  C-3a's line. It needs no `.github/ci-shards.toml` entry: unlisted items run at
  their kind's default weight.

## Findings

No P1 or P2 findings in the change. Points a reviewer should check:

- **Where the comparison sits.** It runs after the initializers, because the RPO
  planner and controller set their positions there. So it runs after phase 1's
  restores of the activity flags, the interlink flags and the callbacks' run state.
  Those restores write only the run's own parameters, and the run's spacecraft
  records, which are a copy under `isolate_state=true`. With `isolate_state=false`,
  a refused resume leaves the caller's spacecraft records holding the checkpoint's
  callback state, and its models reset by their initializers. Main's existing
  refusals at the same two points do the same: the models check in phase 1 and the
  "run state not in this checkpoint" check in phase 3. No model's
  `restore_checkpoint_state!` runs before the comparison. A test checks that a
  refused manager is left as its initializer reset it.
- **What the record compares.** Scopes only, position by position in each group,
  plus the number of models in each group. Model types stay with the `models`
  entry, as before. Two consequences:
  - A type swap at a position with an unchanged scope behaves as on main. An
    existing test relies on that refusal coming from the `models` check.
  - A resume with another number of guidance, navigation or control models is now
    refused, even when they all act on every spacecraft and keep no state. On main
    that resumed. This is deliberate: the scopes cannot be paired otherwise, and
    the file is then from another configuration.
- **Bound forms.** `BoundSpacecraft((2, 1))` and `BoundSpacecraft((1, 2))` compare
  equal, and so do a bound scope and a selection naming the same spacecraft. The
  engine ticks the same spacecraft for each. A model that gives meaning to the
  order of its indices keeps that in its own configuration and run state.
  `AllSpacecraft()` and a bound scope naming every spacecraft stay distinct.
- **Selections.** Guidance, navigation and control models cannot use a
  `SpacecraftSelection` in a run yet: `check_spacecraft_scopes` refuses it. Its form
  is defined so C-3b inherits it. Resolving it calls the selection's `where` once
  more. C-3b should hand over the positions its table resolves, so a predicate
  stays called once per run start.
- **Older checkpoints (the legacy rule).** Accepted as on main, recommended over a
  refusal.
  - Checkpoints belong to long runs in progress. A refusal would restart every
    checkpointed run with GNC models after an upgrade, to catch a change that the
    warning now names.
  - The activity entry follows the same rule for older files.
  - The first resume from such a file goes unchecked; the checkpoints it writes
    carry the entry.
  - A refusal is a one-line change if Giusy prefers it.
- **A run without GNC models writes the entry** with empty groups. So a missing
  entry always means an older file, and such a run resumed with a bound model is
  refused rather than treated as legacy. Checkpoint files of every run gain this
  key. No reader of checkpoint files outside the engine depends on the key set.
- **Models that pick a spacecraft without declaring a scope.** A model with an
  index field but the default `AllSpacecraft()` scope is recorded as `:all`, and a
  changed index is not caught. The extension guide now says to declare
  `spacecraft_scope` for such a model. All built-in index-bound models declare it.

## Residual Risk

- **The first resume from an older checkpoint is not checked.** It is warned when
  a bound or coupled model is present. A user who changed a model's scope between
  writing such a checkpoint and resuming it gets main's behaviour, with the warning.
- **The comparison follows phase 1's restores** (see Findings). A refused resume
  under `isolate_state=false` leaves the caller's spacecraft records with the
  checkpoint's callback state, as main's other refusals at those points do.
- **Models without a declared scope** that select a spacecraft by a field are not
  covered. The guide asks such models to declare `spacecraft_scope`.
- **C-3b.** Its table is built after the restore, from the models. The comparison
  here makes the scopes it reads on a resume equal to the checkpoint's. C-3b's
  design text should say so instead of "the models' checkpoints restore it". If
  C-3b allows `SpacecraftSelection` for guidance, navigation and control models, it
  should feed this record its resolved positions so `where` runs once.
