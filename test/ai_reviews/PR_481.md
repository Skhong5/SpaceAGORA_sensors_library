## Findings

No P1 or P2 findings.

Points a reviewer should check:

- **What the docstring states:**
  - one `solver_trace` entry per checkpoint segment;
  - the final segment's `retcode`, and its `solution` with `return_solution=true`;
  - `retcode` is `nothing` for a run resumed from a checkpoint already at the mission end.

  This matches the metadata return in `run_simulation`:
  - `_solve_run_interval!` pushes one trace entry per solve, and a solver fallback is recorded inside that entry;
  - the checkpoint loop solves once per segment. A run that an event stops early ends in the segment where it stopped, so it has one entry per segment it reached;
  - `last_sol` is the final segment's solution, and stays `nothing` when no segment is solved.

  The in-code comment at the return already says to test the mission rather than the field.
- **The moved sentence:** `return_results=true` with `return_solver_metadata=true` still throws the same `ArgumentError`, and the existing test of it is unchanged. The user guide (`docs/src/user/outputs.md`) already states the restriction this way.
- **Other text:** no other docstring or page said checkpointing and solver metadata cannot be combined.

## P1 Assessment

No P1 findings. Documentation and tests only; the code does not change.

## Tests Added/Updated

Added to `test/unit/simulation_results_tests.jl`, "Solver metadata of a checkpointed run" (5 tests):

- A checkpointed run (1200 s segments over 3600 s) returns `retcode == "Success"`, `solution === nothing` and three trace entries.
- With `return_solution=true`, the solution spans the final segment (2400 s to 3600 s).
- Resumed from its final checkpoint, the run returns `retcode === nothing` and an empty trace.
- Resumed with the mission extended to 4800 s, the run returns `"Success"` and one trace entry.
