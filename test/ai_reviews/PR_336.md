# PR review: robot-arm binding gives each spacecraft its own controller state

## Scope

Review of PR 336 (branch `robot-arm-bind-fresh-state`, head `05e29dedc`) against `main` at `58b8dbc40`: `git diff main...robot-arm-bind-fresh-state`. One commit. `bind_spacecraft(::RobotArmControlEffector, i)` gives the bound copy a deep copy of the controller and a fresh held command. The `bind_spacecraft` docstring now states which members a bound copy owns.

Authorship disclosure: the author of the PR drafted this record. It lists what the author checked and what the independent reviewer must verify; it does not replace that review.

- `src/models/gnc/control/control_hooks.jl`: the `RobotArmControlEffector` method of `SimulationLifecycle.bind_spacecraft` sets `b.controller = deepcopy(m.controller)` and `b.held = RobotArmHeldActuation()` on the shallow copy.
- `src/models/gnc/interfaces/simulation_lifecycle.jl`: `bind_spacecraft` docstring. A member that holds one spacecraft's run state needs its own copy; members indexed by spacecraft (such as `ApolloDescentState`) stay shared.

Outside `src/`: `test/unit/spacecraft_gnc_tests.jl` (a new binding test, and one existing assertion inverted).

## Findings

Author's notes for the reviewer (no P1 or P2 known to the author):

- Low, scope: on `main` the shared state changed no output. `robot_arm_joint_mpc_control` writes `U_prev` (`robot_arm_control.jl:127-128`) and nothing reads it (the solve is `ctrl.H \ rhs`; the only other `U_prev` access in `src/` is the RPO controller reset in `planner_lifecycle.jl:127`). `calcControlEffect!` assigns a new `RobotArmHeldActuation` to `held` on every tick (`robot_arm_control.jl:196`) and never changes it in place. The fix removes a latent coupling.
- Low, behaviour change by design: the per-spacecraft GNC testset pinned `bound.held === arm.held` ("retain nested mutable members"). That assertion is inverted.
- Note: the copy's controller starts from the template's current values, including any `U_prev` left by an earlier run with `isolate_state=false`. That matches what the shared object held before; resetting the warm start at run start is a separate question for the GNC runtime work.
- Note: `controller` is typed `Any`; `deepcopy` also handles `nothing` (the default) and user-defined controllers.

Reviewer to verify:

- Only effectors declared on a spacecraft pass through `bind_spacecraft` (`_flatten_spacecraft_gnc`, `execution.jl:405-416`); configuration-level robot-arm effectors, which every tracked example and test except the binding tests uses, are unchanged.
- The `plan` stays shared and is not mutated during a run (`RobotArmPlan` is an immutable struct; the effector only samples it).
- The new binding test fails on `main` (the first controller-identity assertion), and the inverted assertion fails on `main`.
- The docstring sentence agrees with the other built-in methods: the momentum manager gives the copy its own `mounted_levels`, and the Apollo models share `state` and `actuators`, which are indexed by spacecraft.
