# Review record: PR 453: the gravity backbone refuses a density model

## Scope

Review of the SpaceAGORA `backbone-density-refusal` branch against main
(`6183d00d2`): the fix for item 1 of §14 of the C-2 effector scope design of
2026-10-20, "`gravity_backbone_split` with a density model set fails mid-run".

On main:

- `solver_mode=:gravity_backbone_split` integrates position and velocity as a
  `SecondOrderODEProblem`. Its state is an `ArrayPartition`, which has no `sc`
  field.
- `get_callbacks` leaves the density, thermal, entry-end and drag-state callbacks
  out in backbone mode. It takes that mode from the process setting
  (`SPACEAGORA_SOLVER_MODE` or an active `SimulationEngineConfig`), not from the
  run's `SolverConfig`.
- Chosen by `SolverConfig(solver_mode=:gravity_backbone_split)` under another
  process mode, a run with a density model got the density callback. At the first
  step the callback read `integrator.u.sc` and failed with `FieldError: type
  ArrayPartition has no field sc` (`density_callbacks/runtime.jl:348`, the
  per-spacecraft path; the batch path at :434 reads the same field). It
  reproduces with J2 gravity only, one spacecraft and 60 s.
- Chosen by `SPACEAGORA_SOLVER_MODE`, the same run completed and ignored the
  atmosphere. Its trajectory was bitwise the vacuum run's, and it reported zero
  heat rate and heat load. Tsit5 with the same model reports non-zero values.

Decision: refusal, not support. To support an atmosphere, the backbone would
need density and thermal callbacks that read the partition, and a heat-load state
it does not carry. The backbone already refuses atmosphere-dependent effectors,
and the solver documentation already said it did not support atmospheric runs.

Change: `_gravity_backbone_reject_reason` is the backbone's admission check, and
`_solve_with_solver_policy` runs it before every backbone solve. Its new last
rule refuses a density model other than `NoAtmosphereModel()` and names the
model. Both ways of choosing the mode reach this check before any callback runs.

Authorship disclosure: this record was drafted by the author of the PR; it does
not replace an independent review.

Independent review: the coordinator reviewed PR 453 at `575757be7` under Giusy's
delegation on 2026-10-20. It was a read-only review of the diff, without rerunning
the tests.

- **Where the rule lives.** The new refusal is the last check in
  `_gravity_backbone_reject_reason`, the backbone's existing admission function.
  So it is reached by both ways of choosing the mode, `SolverConfig` and
  `SPACEAGORA_SOLVER_MODE`, and runs the function already admits are unaffected.
  Its message has the same prefix and form as that function's other refusals.
- **Refuse, not support.** It is the right choice for now. The backbone state has
  no field the density and thermal callbacks can read, and no heat-load state, so
  supporting an atmosphere would mean new callbacks rather than a fix.
- **The behaviour change.** A backbone run chosen through the environment
  variable with a density model used to complete with zero heating, and is now
  refused. It is stated in the PR and in `solver_configuration.md`, and no test,
  example or page ran such a configuration.
- **The probe change.** The state-anchor probe's backbone assertion moves to
  vacuum so it keeps testing the anchor's own refusal rather than the new one.
- **Left for later.** `get_callbacks` still reads the backbone mode from the
  environment rather than `SolverConfig`. It is named as a separate change,
  after C2a (#449), which owns that file.
- `git merge-tree` is clean with main `6d77179ba` and with #448, #449, #450 and
  #451. There is no trailer, and `## Changed Files` lists the one `src` file.

## Findings

No P1 or P2 findings in the change. Points a reviewer should check:

- Deliberate behaviour change: a backbone run chosen by
  `SPACEAGORA_SOLVER_MODE` with a density model set completed on main, ignored the
  atmosphere and reported zero heating; it is now refused. No test, example or
  documentation page runs one. Every backbone run in the tests uses
  `NoAtmosphereModel()`, and the state-anchor probe's backbone assertion expected
  a refusal anyway (see Tests).
- Follow-up, not fixed here: `get_callbacks`
  (`callbacks/density_callbacks/assembly.jl:200`) takes `backbone_mode` from the
  process solver mode. The same function's `output_solver_mode` (:284) prefers
  `args.solver_config`. A vacuum backbone run chosen by `SolverConfig` therefore
  still installs first-order callbacks:
  - the planet-frame update: for the reproduction configuration, `get_callbacks`
    returns one more discrete callback than for the same run chosen by
    `SPACEAGORA_SOLVER_MODE`;
  - the data-saving callback, when results are recorded.
  Both runs' results tables have the same rows (20, 40 and 60 s). After this change
  no atmosphere callback can reach a backbone run, because all of them need a
  density model. Fixing the mismatch would change which callbacks such runs
  install, and the file is in the C2a callback-phase area, so it is left for a
  separate change.
- Low: the refusal comes at the start of the solve, after setup. The
  atmosphere-without-drag warning prints first, and with checkpointing on, the
  checkpoint is loaded first. The existing backbone rules have the same timing.
  Nothing writes result files before the solve.
- Low: the rule reads `environment_model.density_model` only. Per-spacecraft
  density instances are copies of it (`_initialize_density_model_instances!`), so
  there is no other density source to check.
- Low: the rule is the last one, so a configuration that also breaks an earlier
  rule gets the earlier message, as before. The existing refusal tests assert those
  messages.

## P1 Assessment

No P1 findings. The change adds one refusal at the end of an admission check.
Every configuration the check admits passes through the function exactly as on
main.

Unresolved P1: No
